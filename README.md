# Система прогнозирования продаж для сети дарксторов «Прилавок»

**База данных для проверки ревьюером:** PostgreSQL, база `playground_ds_20260915_ff9d3b0716` (user `ds_20260915_ff9d3b0716`). Все подключения — через Airflow Connection и переменные окружения; креды в коде репозитория отсутствуют.

---

## 1. Описание проекта

**Бизнес-задача.** Сеть «Прилавок» (45 дарксторов) планирует закупки вручную: дефицит в пиковые периоды стоит 3–5% выручки, избыточные запасы и списания — 2–3%, аналитики тратят 15–20 часов в неделю на ручное планирование.

**Цель.** Автоматизированное прогнозирование недельных продаж для каждой пары «даркстор × отдел» моделью CatBoost в режиме пакетного внедрения: переобучение/инференс каждое воскресенье в 20:00, к утру понедельника прогнозы готовы для системы закупок.

**Подход.** Проект состоит из двух частей: исследовательская (Jupyter Notebook: EDA, feature engineering, PSI-мониторинг, обучение и оценка модели) и производственная (Airflow DAG батч-инференса, пишущий прогнозы в витрину Postgres).

## 2. Описание данных

| Таблица | Объём | Состав | Период |
|---|---|---|---|
| `sales` | 421 570 × 5 | store, dept, date, weekly_sales (цель), is_holiday | фев 2023 — окт 2025 |
| `stores` | 45 × 3 | store, type (A/B/C), size | — |
| `features` | 421 570 × 12 | temperature, fuel_price, factor1–5 (маркдауны), cpi, unemployment | фев 2023 — окт 2025 |
| `plan` | 115 064 строки | те же столбцы, что `sales`, без `weekly_sales` | ноя 2025 — июл 2026 |

**Особенности данных и решения:**
- пропуски только в маркдаунах `factor2`–`factor5` (64–74%) — заполнены 0 (пропуск = акции не было);
- отрицательные продажи (возвраты) скорректированы `clip(lower=0)`: удаление строк разрушило бы недельную панель и лаговые признаки;
- полных и ключевых дубликатов не обнаружено;
- сезонность: пики на 47-й и 51–52 неделях (Чёрная пятница, Новый год), праздничные недели в среднем 50.5 млн руб. против 46.9 млн у обычных, тренд стабильный;
- аномально высокие продажи (порог 99.99% = 283 659.72 руб., 43 записи) — реальные сезонные пики (72.1% праздничных недель против 7.0% в базе, тип A, отдел 72) — сохранены;
- *примечание к таблице `plan`:* в исходном виде не содержит целевого признака; на этапе задачи `load_data` принудительно дополняется как `NULL AS weekly_sales` для сохранения единой структуры при `UNION ALL`.

## 3. Описание признаков

Все признаки строятся только на информации до даты прогноза (защита от утечки данных):

- `avg_sales_before` — средние продажи пары (store, dept) строго по данным до текущей даты (`expanding().mean()` + `shift(1)`);
- `sales_1week_ago`, `sales_2week_ago`, `sales_4week_ago` — календарные лаги через сдвиг дат (`DateOffset` + `merge`): устойчиво к дырам недельной сетки;
- `mean_sales_2week`, `mean_sales_4week` — скользящие средние за 2 и 4 предыдущие недели (текущая неделя в окно не входит);
- контекст: `store`, `dept`, `is_holiday`, `type`, `size`.

Временные признаки (`month`, `quarter`, `year`, `week`) создавались, но удалены по итогам PSI-мониторинга (см. ниже). Итоговый контракт модели — 11 признаков; он зафиксирован константой `MODEL_FEATURES` в `dags/preprocessing.py`, там же контракт типов `FEATURE_DTYPES`.

## 4. Логика обучения

**Разделение по времени:** обучение — фев 2023 — авг 2025, валидация — сен — окт 2025 (имитация реальной работы: прогноз будущего по прошлому).

**PSI-мониторинг:** значительный дрейф (PSI ≥ 0.2) у 13 признаков — календарных (`week` 6.86, `month` 6.49, `quarter` 4.55, `year` 2.85), сезонных (`temperature` 0.95, маркдауны 0.63–1.94) и трендовых макро (`fuel_price` 4.27, `cpi` 2.84, `unemployment` 0.43). Дрейф объясним природой временного разбиения (валидация — узкое осеннее окно), не ошибкой данных; по правилам мониторинга эти признаки удалены из обеих выборок. Стабильны: лаги и скользящие (PSI ≈ 0.001–0.002), идентификаторы (0.0), `is_holiday` (0.05).

**Модель:** `CatBoostRegressor`, iterations=500, learning_rate=0.1, depth=6, random_state=42, `cat_features=['type']` (ordered-статистики без утечки).

**Качество:**

| Выборка | MAE, руб. | RMSE, руб. | R² |
|---|---|---|---|
| train | 1 769.91 | 4 199.17 | 0.9664 |
| val | 1 581.51 (10.0% от средних недельных продаж) | 4 002.57 | 0.9667 |

Разрыва метрик нет — переобучение отсутствует.

**Важность признаков:** `sales_1week_ago` 29.0%, `mean_sales_2week` 14.6%, `sales_4week_ago` 14.0%, `dept` 7.6%, `is_holiday` 7.0%; утечек в топе нет (целевая переменная и дата в признаки не входят).

**Артефакт:** модель сохранена в S3-бакет `s3-ds-20260915-ff9d3b0716`, ключ `catboost_model.pkl`.

## 5. Архитектура пайплайна batch-инференса

DAG `sales_prediction_batch_inference`, расписание `0 20 * * 0` (воскресенье, 20:00):

```
load_data ──> preprocess_features ──┐
                                    ├──> run_inference ──> save_predictions
load_model ─────────────────────────┘
```

- **load_data** — собирает в БД временную таблицу `inference_data_temp` (`sales` UNION ALL `plan` + join `features` и `stores`); логирует строки/границы дат; передаёт в XCom первую дату плана (2025-11-02). Большие данные через XCom не передаются.
- **preprocess_features** — читает temp-таблицу, применяет `preprocess_data()` из `dags/preprocessing.py` (логика идентична обучению), оставляет строки плана, удаляет `weekly_sales`, заполняет лаги нулями, `dropna()`, передаёт компактный df через XCom (`.to_json()`), удаляет temp-таблицу.
- **load_model** — скачивает модель из S3 во временный файл, в XCom передаёт путь.
- **run_inference** — `predict` по контракту `MODEL_FEATURES` с восстановлением типов (`ensure_model_dtypes`), клиппинг отрицательных прогнозов до 0; реализована валидация на пустой датасет плана с передачей пустой схемы для защиты графа от падения; результат в XCom.
- **save_predictions** — пишет витрину `predictions` (PK: store, dept, date; ON CONFLICT — обновление), логирует количество строк и первые 5 строк.

**Источники:** Postgres (`sales`, `plan`, `features`, `stores`), S3 (модель).
**Артефакты:** S3 (`catboost_model.pkl`), Postgres (таблица `predictions`).
**Секреты:** Airflow Connection `postgres_sales_db` и Variables `s3_access_key`, `s3_secret_key`, `s3_bucket_name`, `s3_model_key`; в ноутбуке — `.env` (файл в `.gitignore`).

## 6. Инструкция по запуску

**Локально (обучение):**
1. `git clone <ssh-адрес репозитория> && cd prilavok-project`
2. `pip install -r requirements.txt`
3. Создать `.env` с ключами БД и S3 (переменные `DB_NAME`, `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `S3_ACCESS_KEY_ID`, `S3_SECRET_KEY`, `S3_BUCKET`).
4. Открыть `model_training.ipynb`, выполнить Kernel → Restart & Run All: тетрадь обучит модель и сохранит её в S3.

**Airflow (инференс):**
1. Запустить сниппет платформы `===Запуск Airflow===`, вставив SSH-адрес репозитория.
2. Admin → Connections: создать `postgres_sales_db` (Postgres, параметры БД).
3. Admin → Variables: создать `s3_access_key`, `s3_secret_key`, `s3_bucket_name`, `s3_model_key` (= `catboost_model.pkl`).
4. Trigger DAG `sales_prediction_batch_inference`; контроль — вкладка Graph (все задачи зелёные) и логи задач.
5. По завершении работы — сниппет `===Остановка Airflow===`.

## 8. Ограничения и известные особенности

- Прогнозы на горизонте 2+ недели плана занижены: фактических продаж предыдущих недель плана не существует, лаги заполнены нулями по постановке задачи (видно в витрине со второй недели плана). Для горизонта одной недели проблема закрыта недельным циклом инференса; развитие — рекурсивный инференс или переобучение по мере накопления факта.
- 36 строк плана (0.03%) удалены `dropna()` как пары без истории для агрегатов.
- Дрейф сезонных признаков в PSI — ожидаемое следствие временного разбиения, учтён при отборе.
