# Система прогнозирования продаж для сети дарксторов «Прилавок»

**База данных для проверки ревьюером:** PostgreSQL, база `playground_ds_20260915_ff9d3b0716` (user `ds_20260915_ff9d3b0716`). Все подключения — через Airflow Connection и переменные окружения; креды в коде репозитория отсутствуют.

---

## 1. Описание проекта

**Бизнес-задача.** Сеть «Прилавок» (45 дарксторов) планирует закупки вручную: дефицит в пиковые периоды стоит 3–5% выручки, избыточные запасы и списания — 2–3%, аналитики тратят 15–20 часов в неделю на ручное планирование.

**Цель.** Автоматизированное прогнозирование недельных продаж для каждой пары «даркстор × отдел» моделью CatBoost в режиме пакетного внедрения: каждое воскресенье в 20:00 DAG обновляет прогнозы в витрине; модель обучается отдельно в `model_training.ipynb` и загружается из S3, переобучение — по мере накопления факта.

**Подход.** Проект состоит из двух частей: исследовательская (Jupyter Notebook: EDA, feature engineering, PSI-мониторинг, обучение и оценка модели) и производственная (Airflow DAG батч-инференса, пишущий прогнозы в витрину Postgres).

## 2. Описание данных

| Таблица | Объём | Состав | Период |
|---|---|---|---|
| `sales` | 421 570 × 5 | store, dept, date, weekly_sales (цель), is_holiday | фев 2023 — окт 2025 |
| `stores` | 45 × 3 | store, type (A/B/C), size | — |
| `features` | 421 570 × 12 | temperature, fuel_price, factor1–5 (маркдауны), cpi, unemployment | фев 2023 — окт 2025 |
| `plan` | 115 064 строки | те же столбцы, что `sales`, без `weekly_sales` | ноя 2025 — июл 2026 |

**Особенности данных и решения:**
- пропуски только в маркдаунах `factor2`–`factor5` (64–74%) — заполнены 0 (пропуск = акции не было);
- отрицательные продажи (возвраты, 0.30% строк) скорректированы `clip(lower=0)`: удаление строк разрушило бы недельную панель и лаговые признаки;
- полных и ключевых дубликатов не обнаружено;
- сезонность: пики на 47-й и 51–52 неделях (Чёрная пятница, Новый год), праздничные недели в среднем 50.5 млн руб. против 46.9 млн у обычных, тренд стабильный;
- аномально высокие продажи (порог 99.99% = 283 659.72 руб., 43 записи) — реальные сезонные пики (72.1% праздничных недель против 7.0% в базе, тип A, отдел 72) — сохранены;
- *примечание к таблице `plan`:* в исходном виде не содержит целевого признака; на этапе задачи `load_data` принудительно дополняется как `NULL AS weekly_sales` для сохранения единой структуры при `UNION ALL`.

## 3. Описание признаков

Все признаки строятся только на информации до даты прогноза (защита от утечки данных):

- `avg_sales_before` — средние продажи пары (store, dept) строго по данным до текущей даты (`expanding().mean()` + `shift(1)`);
- `median_sales_before` — медиана той же пары по той же схеме (`expanding().median()` + `shift(1)`): устойчива к выбросам, праздничный пик не перекашивает базовый уровень пары;
- `sales_1week_ago`, `sales_2week_ago`, `sales_4week_ago` — календарные лаги через сдвиг дат (`DateOffset` + `merge`): устойчиво к дырам недельной сетки; внутренние лаги 1–12 недель используются для расчёта окон и в модель не входят;
- `mean_sales_2week`, `mean_sales_4week`, `mean_sales_8week`, `mean_sales_12week` — скользящие средние за 2/4/8/12 предыдущих недель (текущая неделя в окно не входит); длинные окна описывают среднесрочную и квартальную динамику спроса;
- контекст: `store`, `dept`, `is_holiday`, `type`, `size`.

Временные признаки (`month`, `quarter`, `year`, `week`) создавались, но удалены по итогам PSI-мониторинга (см. ниже). Итоговый контракт модели — 14 признаков; он зафиксирован константой `MODEL_FEATURES` в `dags/preprocessing.py`, там же контракт типов `FEATURE_DTYPES` и функция восстановления типов `ensure_model_dtypes()`.

## 4. Логика обучения

**Разделение по времени:** обучение — фев 2023 — авг 2025 (375 744 строки), валидация — сен — окт 2025 (23 094 строки); периоды не пересекаются (имитация реальной работы: прогноз будущего по прошлому).

**PSI-мониторинг:** значительный дрейф (PSI ≥ 0.2) у 13 признаков — календарных (`week` 6.86, `month` 6.49, `quarter` 4.55, `year` 2.85), сезонных (`temperature` 0.95, маркдауны 0.63–1.94) и трендовых макро (`fuel_price` 4.27, `cpi` 2.84, `unemployment` 0.43). Дрейф объясним природой временного разбиения (валидация — узкое осеннее окно), не ошибкой данных; по правилам мониторинга эти признаки удалены из обеих выборок. Стабильны: лаги, скользящие (включая окна 8/12), `avg_sales_before`, `median_sales_before` (PSI ≈ 0.0007–0.0029), идентификаторы (0.0), `is_holiday` (0.05).

**Модель:** `CatBoostRegressor`, iterations=500, learning_rate=0.1, depth=6, random_state=42, `cat_features=['store', 'dept', 'type']`: идентификаторы переданы как категории, поскольку сплиты по числовым диапазонам («dept < 47.5») для них бессмысленны, а target-статистики честнее.

**Качество:**

| Выборка | MAE, руб. | RMSE, руб. | R² |
|---|---|---|---|
| train | 1 779.23 | 4 244.30 | 0.9657 |
| val | 1 586.60 (10.0% от средних недельных продаж) | 4 164.92 | 0.9640 |

Разрыва метрик нет — переобучение отсутствует.

**Важность признаков:** `sales_1week_ago` 27.30%, `mean_sales_2week` 16.32%, `mean_sales_8week` 8.26%, `mean_sales_12week` 8.10%, `sales_2week_ago` 7.63%, `is_holiday` 6.66%; исторические признаки суммарно ~87.2%. Утечек в топе нет (целевая переменная и дата в признаки не входят).

**Артефакт:** модель сохранена в S3-бакет `s3-ds-20260915-ff9d3b0716`, ключ `catboost_model.pkl` (1.37 МБ).

## 5. Архитектура пайплайна batch-инференса

DAG `sales_prediction_batch_inference`, расписание `0 20 * * 0` (воскресенье, 20:00):

```
load_data ──> preprocess_features ──┐
                                    ├──> run_inference ──> save_predictions
load_model ─────────────────────────┘
```

- **load_data** — собирает в БД временную таблицу `inference_data_temp` (`sales` UNION ALL `plan` + join `features` и `stores`); логирует строки/границы дат (536 634 строки, 2023-02-05 → 2026-07-26); передаёт в XCom первую дату плана (2025-11-02). Большие данные через XCom не передаются.
- **preprocess_features** — читает temp-таблицу через SQLAlchemy-движок, применяет `preprocess_data()` из `dags/preprocessing.py` (логика идентична обучению), оставляет строки плана, удаляет `weekly_sales`, заполняет лаги типичным уровнем пары (`avg_sales_before`) там, где продаж предыдущих недель не существует, логирует строки до/после `dropna()` (потерь нет: 115 064 → 115 064), передаёт компактный df через XCom (`.to_json()`), удаляет temp-таблицу.
- **load_model** — скачивает модель из S3 во временный файл, в XCom передаёт путь.
- **run_inference** — `predict` по контракту `MODEL_FEATURES` с восстановлением типов (`ensure_model_dtypes`), клиппинг отрицательных прогнозов до 0; реализована валидация на пустой датасет плана с передачей пустой схемы для защиты графа от падения; результат в XCom.
- **save_predictions** — пишет витрину `predictions` (PK: store, dept, date; ON CONFLICT — обновление), логирует количество строк (115 064) и первые 5 строк.

**Источники:** Postgres (`sales`, `plan`, `features`, `stores`), S3 (модель).
**Артефакты:** S3 (`catboost_model.pkl`), Postgres (таблица `predictions`).
**Секреты:** Airflow Connection `postgres_sales_db` и Variables `s3_access_key`, `s3_secret_key`, `s3_bucket_name`, `s3_model_key`; в ноутбуке — `.env` (файл в `.gitignore`).

**Roadmap (осознанные решения):** передача компактного df через XCom — требование ТЗ; в производственной версии заменяется ссылкой на промежуточную таблицу/S3, как уже сделано для модели (JSON в XCom раздувает метабазу Airflow). Ключи S3 в Variables — требование ТЗ; производственный стандарт — Connection типа AWS с маскированием Secret Key и нативным S3Hook. Тяжёлые импорты перенесены внутрь задач: scheduler не загружает pandas/catboost при разборе файлов dags/.

## 6. Инструкция по запуску

**Локально (обучение):**
1. `git clone <ssh-адрес репозитория> && cd prilavok-project`
2. `pip install -r requirements.txt`
3. Создать `.env` с ключами БД и S3 (переменные `DB_NAME`, `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `S3_ACCESS_KEY_ID`, `S3_SECRET_KEY`, `S3_BUCKET`); шаблон — `.env.example` (`cp .env.example .env`).
4. Открыть `model_training.ipynb`, выполнить Kernel → Restart & Run All: тетрадь обучит модель и сохранит её в S3.

**Airflow (инференс):**
1. Запустить сниппет платформы `===Запуск Airflow===`, вставив SSH-адрес репозитория.
2. Admin → Connections: создать `postgres_sales_db` (Postgres, параметры БД).
3. Admin → Variables: создать `s3_access_key`, `s3_secret_key`, `s3_bucket_name`, `s3_model_key` (= `catboost_model.pkl`).
4. Trigger DAG `sales_prediction_batch_inference`; контроль — вкладка Graph (все задачи зелёные) и логи задач.
5. По завершении работы — сниппет `===Остановка Airflow===`.

## 8. Ограничения и известные особенности

- Недели плана 2+ не имеют фактических лагов; они заполняются типичным уровнем пары (`avg_sales_before`), поэтому прогноз на горизонте 2+ недель соответствует среднему уровню спроса (в витрине для пары (1,1) — 23–28 тыс. руб./неделя), а не около нуля. Фундаментальное улучшение длинных горизонтов — рекурсивный инференс.
- Пары «стор × отдел» без истории получают прогноз: базовые уровни заполняются медианой того же отдела по другим дарксторам; витрина содержит все 115 064 строки плана (dropna в инференсе не теряет строк).
- Дрейф сезонных признаков в PSI — ожидаемое следствие временного разбиения; в производственном мониторинге календарные признаки оцениваются отдельно от формального порога 0.2.
